# 生产维护（Maintenance）

本文档定义 Goo Engine 5.2 生产分支的驱动基线更新、上游跟进、崩溃报告 triage 与发版回滚流程。所有流程都假设“证据优先”：没有对应硬件上的报告，就不声称覆盖。

## 1. 节奏与职责

| 活动 | 频率 | 负责人（占位） |
| --- | --- | --- |
| 驱动基线季度复核 | 每季度首月（1/4/7/10 月）第一周 | 驱动矩阵 owner + 各平台 lab |
| 上游/OS 变更跟踪 | 每月 | 上游跟进 owner |
| 崩溃报告 triage | 每周一次例会 + 按 severity 即时处理 | triage owner |
| gate 矩阵全量运行 | 每次发布前 + 每周一夜跑 | CI/runner owner |
| 发布回滚演练 | 每半年一次 | 发布工程 owner |

季度批次建议固定为：1 月（上一年 Q4 驱动）、4 月（Q1）、7 月（Q2）、10 月（Q3）。批次只调整“最低基线”，不追逐最新 hotfix；最新驱动由 nightly 行先行观察。

当前可执行范围（2026-11）：Windows 11 + Intel Iris Xe 与 Debian 13 + GTX 1660 两行已实跑；其余 Windows/Linux 行仍是 descriptor，不能把“矩阵里有这一行”当作“已验证”。本地门禁用
`python tools/ci/local_gate.py --release-dir dist/goo-engine-5.2.1`（7 阶段；`--with-ctest` 追加 Goo CTest），发布前必须全过。GitHub 托管 runner 不作为本阶段的验收依据；没有对应硬件时，矩阵行只能保持“未覆盖”。

## 2. 季度驱动更新

### 2.1 收集

从官方来源收集候选版本，记录发布日期与 WHQL/推荐状态：

- NVIDIA Windows 显示驱动 / Linux 驱动分支；
- AMD Adrenalin（Windows）与 Mesa（Linux）；
- Intel Arc/Iris Windows 驱动与 Mesa；
- Vulkan SDK / loader（只影响构建与测试工具，不进入 `min_driver`）。

不要使用第三方驱动包、修改版 INF 或来源不明的镜像作为基线证据。

### 2.2 评估与更新

1. 在实验室机器安装候选驱动，先跑 `detect.py` 确认版本被正确识别（尤其 NVIDIA 的归一化版本、AMD/Intel 的 INF 原始版本）。
2. 跑对应行的 gate smoke 与 EEVEE 渲染；保留 `report.json`、日志与渲染图。
3. 对比上一基线：若新驱动引入回归，基线**不升级**，把回归记录到矩阵行的 `notes` 与 issue，并在 nightly 继续观察。
4. 更新 `tools/driver_matrix/matrix.json` 的 `gpu.min_driver`（`display`、`version`、必要时的 `raw_version`）和 `notes`。
5. 同步更新 `docs/production/driver-matrix.md` 的基线表与覆盖说明。
6. 提交 PR：包含矩阵 diff、实验室报告路径、回归对比结论。审批人：驱动矩阵 owner + 发布工程 owner。
7. 合并后在至少一个 gate runner 上重跑，确认 `driver_conformance.status=met`。

### 2.3 紧急更新（安全/严重回归）

安全公告或严重驱动回归可跳过季度窗口：

- 由发布工程 owner 与安全负责人共同批准；
- 只调整受影响的 scheme/行，附厂商公告链接；
- 24 小时内完成 gate 复跑；无法复跑时在发布说明中标注例外，并在 5 个工作日内补证。

## 3. 上游跟进

跟踪对象与关注点：

| 上游 | 关注点 | 频率 |
| --- | --- | --- |
| Blender 上游 | 渲染后端、GPU 模块、驱动兼容修复、EEVEE 变更 | 每周 |
| Goo Engine 下游分支 | 与上游的合并冲突、生产补丁 | 每周 |
| Mesa | AMD/Intel OpenGL/Vulkan 修复、Ubuntu 版本同步 | 每月 |
| NVIDIA / AMD / Intel 驱动 | 已知问题清单、回归、长期支持分支 | 每月 |
| Vulkan-Headers / loader | 构建依赖与验证工具 | 每季度 |
| Ubuntu / Windows | OS 生命周期、WDDM/显示栈变更 | 每季度 |

流程：

1. 订阅 release notes/安全公告；每月整理一次“可能影响图形栈”的条目。
2. 对可疑变更在 nightly 行先跑，不直接进 gate。
3. 需要合入的修复走正常 PR；cherry-pick 策略由发布工程 owner 按风险决定，禁止无记录的直接改源码。
4. 上游行为变化导致矩阵不再成立时，更新矩阵并在文档中记录原因和生效版本。

## 4. 崩溃报告 triage

### 4.1 报告必填字段

收到崩溃报告时先补齐以下信息，缺失则退回补充：

- Goo 版本与 commit（`source.commit`）、构建 ID；
- OS 版本/build、CPU 架构、显示服务器（Windows/X11/Wayland/Quartz）；
- GPU 型号、厂商、驱动版本、驱动 scheme；
- 后端（OpenGL/Vulkan/Metal）与是否可复现；
- 复现步骤、最小场景/文件、崩溃日志/backtrace、`report.json`（如有）；
- 对应矩阵行 ID（不知道则写“未知”）。

### 4.2 分级与时限（占位，需团队确认）

| 级别 | 定义 | 首次响应 | 目标处置 |
| --- | --- | --- | --- |
| S1 | 启动即崩、数据损坏/丢失、安全风险、gate 组合普遍崩溃 | 24 小时 | 72 小时内给 workaround 或回滚决定 |
| S2 | gate 组合上的功能崩溃、可稳定复现 | 3 个工作日 | 当前/下一补丁版本修复 |
| S3 | nightly/advisory 组合崩溃、难复现 | 5 个工作日 | 排期修复或记录为已知问题 |
| S4 | 外观/性能问题、不影响正确性 | 10 个工作日 | 进入 backlog |

### 4.3 分类与去重

1. 按崩溃栈顶层帧 + GPU/驱动/后端聚类，合并重复报告。
2. 判定根因类别：
   - **应用缺陷**：进入正常修复流程，补回归测试；
   - **驱动缺陷**：在最低基线与最新驱动上各复现一次，整理厂商所需信息（驱动版本、OS、GPU、复现步骤、日志、dump），提厂商工单；
   - **不支持配置**：对照 `matrix.json` 的 `backends`/`min_driver`，明确告知支持边界；
   - **环境/安装问题**：转支持流程，不占用图形 triage 配额。
3. 若问题暴露矩阵缺口（如某集显组合完全未覆盖），创建矩阵行或记录“明确不支持”，不要用“其他机器正常”关闭。

### 4.4 驱动问题的升级路径

- 先在受影响行的最低驱动与最新驱动上复现，确认是否与驱动版本相关；
- 收集厂商要求的系统信息与 dump，提工单并记录工单号；
- 在矩阵行 `notes` 记录“已知驱动问题 + 影响版本 + workaround”；
- 若最新驱动修复，季度基线评估时提升；若最低驱动受影响且无 workaround，评估提升最低基线或增加例外说明；
- 关闭条件：修复版本在 gate runner 复跑通过，或明确标记为不支持并更新文档。

## 5. 发版回滚

### 5.1 触发条件

满足任一条件即启动回滚评估（由发布工程 owner 裁决）：

- 下载产物的 SHA256 与 `SHA256SUMS`/manifest 不一致，或签名验证失败；
- gate 组合上出现 S1 回归（启动崩溃、数据损坏、安全漏洞）；
- 安装器/打包错误导致大范围无法安装；
- 发布 manifest 的 commit/build ID 与实际构建不符；
- 许可证/合规问题。

### 5.2 步骤

1. **停止继续推广**：暂停下载页/自动更新推送/镜像同步；保留现有资产，不删除证据。
2. **标记撤回**：在发布页与内部记录标注“withdrawn/回滚”，写明受影响版本、平台、校验和与原因；不要复用旧版本号。
3. **给出替代版本**：指向最近一个通过 gate 的版本，附其 manifest 与校验和。
4. **重建**：从 tag 对应的 commit 重新构建；重新签名；重新生成 `SHA256SUMS` 与 manifest；跑 `verify_release.py`（必要时 `--require-signed --check-signatures`）。
5. **重发**：使用补丁版本号（如 `5.2.1`），更新发布记录与公告；下载后再次校验。
6. **复盘**：5 个工作日内完成 postmortem，包含时间线、根因、为何 gate 未拦截、改进项（矩阵/测试/流程）与责任人。
7. **矩阵修正**：若回滚暴露出未覆盖的硬件/驱动组合，按第 2 节或矩阵变更流程补行，并在下一次 gate 运行中验证。

### 5.3 驱动基线回滚

若确认是新基线驱动导致回归：

- 将 `matrix.json` 的 `min_driver` 回退到上一基线，并在 `notes` 记录原因与厂商 issue；
- 重新跑受影响 gate 行；
- 发布说明中注明驱动要求变化，避免用户在新驱动上重复踩坑；
- 不是“回滚驱动安装包”，而是回滚我们对最低支持的声明。

## 6. 变更审计

- 矩阵与发布脚本的变更必须走 PR，禁止直接推送生产分支；
- 发布产物、manifest、校验和按版本归档，保留至少一个支持周期；
- 驱动基线变更需可追溯到实验室报告或厂商公告；
- 回滚与例外需记录批准人、时间与理由。

## 7. 已知缺口（诚实清单）

- 当前只有两条真实硬件行（Windows 11 + Iris Xe、Debian 13 + GTX 1660）；其余 13 行 Windows/Linux 行未覆盖，没有自托管 GPU lab，也没有长期 nightlies。本文档的 gate 流程是目标状态，不是全矩阵已运行状态。
- 本地门禁已实现并 7/7 通过；GitHub 托管 CI 仍有 runner 队列/平台限制，因此不作为本阶段验收项。
- 没有历史崩溃数据，severity/SLA 数值均为占位，需团队按实际人力确认。
- 未定义具体的厂商工单账号与升级联系人（TBD）。
- 未在真实发布上执行过回滚演练；首次演练需在非生产版本上进行并记录。
- 季度日期是建议节奏，需与发布日历对齐后固化。
